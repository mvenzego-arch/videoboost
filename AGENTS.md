# VideoBoost — правила проектной команды (эра C#)

Проект Flash: **VideoBoost v3** — C# .NET 8 + WinUI3 (Windows App SDK).
Питон-версия сохранена на ветке `legacy-python` (тег `v2.0-py-final`) — читать её
как справочник пайппайна (FFmpeg/Real-ESRGAN/RIFE команды, логика пресетов),
но не копировать вслепую: C#-эквиваленты пишутся заново, аккуратно.

## Стек (закреплён решением владельца)

- **Язык / рантайм:** C# 10+ на .NET 8, WinUI3 (Microsoft.WindowsAppSDK).
- **Только CLI-сборка:** `dotnet build`, `dotnet publish` — Visual Studio не требуется.
  Вёрстка — XAML в файлах, редактируется агентами напрямую.
- **Бэкенд-движки остаются нативными**: FFmpeg, Real-ESRGAN ncnn Vulkan,
  RIFE ncnn Vulkan — запускаются как процессы (`Process`), конфиг команд
  соответствует legacy-версии, которая уже доказанно работает.
- Никаких новых серверных зависимостей без явного решения владельца;
  NuGet-пакеты для WinUI3 и логов — допустимы (CommunityToolkit, Serilog).

## Автоконвейер для новых фич

Получая запрос, основной агент сам делегирует суб-агентам (от владельца не нужно
знать имён). Порядок:

1. `ux-designer` — спека интерфейса (XAML-макет, состояния, потоки). Контрольная точка.
2. `visual-prompter` — промты графики, если нужны ассеты.
3. После утверждения спеки — `ui-dev` (XAML/WinUI3) и `engine-dev` (С# пайплайн).
4. `ui-copywriter` — тексты элементов.
5. Параллельно: `test-writer` (xUnit) и `code-reviewer` (ревью диффов).
6. `perf-guardian` — если менялись tile/тайминги процессов (VRAM 4 ГБ норм).
7. `docs-writer` — README/changelog.
8. Контрольная точка: владелец проверяет сборку (`dotnet build`) и окно на своей машине.

## Баги

`screenshot` → `vision-triage` (описание дословно) → `debugger` (диагноз с доказательством)
→ точечный фикс (`winui-dev`/`engine-dev`) → регресс-тест xUnit → ревью.

## Жёсткие правила (для всех агентов)

- **Стек зафиксирован решением владельца: C# .NET 8 + WinUI3.** Возврат на Python,
  переписывание на другой язык/фреймворк — только через явное решение владельца
  после расчёта цены.
- Сборка обязана проходить локально: `dotnet build` без ошибок и предупреждений
  в зоне агента; тесты `dotnet test` — зелёные.
- GUI не блокируется: процессы — через `async/await`, прогресс — `IProgress<T>`,
  обновление UI — только в UI-потоке (`DispatcherQueue`).
- Пути через `Path.Combine`, `Environment.ProcessPath`; кириллица/пробелы в путях — норма.
- Отмена обязательна: `CancellationToken` на вsе процессы; temp-файлы чистятся.
- Ошибка пользователя видна в журнале, окно не падает.
- Долгие команды не съедают память: очередь писем в движке, какой из процессов
  убивается — по root-process, потом дети (`taskkill /T`-эквивалент, `Process.Kill(entireProcessTree: true)`).
- Профиль дистрибутива: `dotnet publish -c Release -r win-x64 --self-contained false`
  «лёгкий» (нужен .NET на машине) vs `--self-contained true` «толстый» (80–150 МБ) —
  решение принимает владелец на контрольной точке.
